# Atoma adapter implementation and test plan

Intended file: .claude/plans/atoma-vault-deposit-manager.md.
Status: approved for implementation. Reviewed with Claude CLI Opus 5.5 on 2026-10-28; second pass returned no blocking findings. No funded live round trip is authorised.

## Goal and evidence

Implement complete synchronous deposits and asynchronous request/epoch/claim redemptions for both existing Arbitrum Atoma deployments: Index (0xcc56410e1a136af0eceb7241c6ae394f4d8b581c), traded by NB05, and RWA (0x1c788e14d8e5b446e3f71b5142e2edabcab36da1). Scope is eth-defi adapters, persistence interfaces, Guard/Safe integration, tests and documentation. Executor portfolio accounting and backtest changes are a subsequent consumer integration; document their obligations. No production transactions, deployments, database migrations, push or PR are part of this work.

Starting point: AtomaVault has classification, names, tags, fee metadata and withdrawal discovery, but inherits ERC4626DepositManager; direct withdraw/redeem are disabled and no complete public capability is certified. Reuse the shared VaultDepositManager interfaces, Plutus request/ticket/claim structure and guarded lifecycle tests, Gains receipt validation and epoch tickets, and Accountable/Ember indexed pending-flow recovery. Do not copy another protocol's settlement rules.

Sources: PR https://github.com/tradingstrategy-ai/web3-ethereum-defi/pull/1691 and its checked-in NB05 assessment; verified implementation https://arbiscan.io/address/0x9161be115867c347adfb4c88a80e759920de86dc#code (retrieved through Etherscan v2); previous implementation https://repo.sourcify.dev/42161/0x9521B08303AE010e85e24fC15D5334A0E506641E. On 2026-10-28, read-only RPC checks at block 519150162 found BOTH proxies using 0x9161be115867c347adfb4c88a80e759920de86dc, three-day epochs, native USDC (0xaf88d065e77c8cC2239327C5EDb3A432268e5831), 12-decimal shares and MIN_DEPOSIT=100000000 raw USDC. At canonical ARBITRUM_MIDNIGHT_BLOCK=487039644 both proxies use 0x9521b08303ae010e85e24fc15d5334a0e506641e; Index has seven-day epochs and RWA one-hour epochs. The adapter's older Index implementation link is stale; never infer current semantics from that link.

Verified current lifecycle:
- Deposits accrue performance fees before minting; previewDeposit need not predict the executed share count exactly. Deposits lock only newly deposited shares for the receiver's current epoch. Older unlocked shares remain withdrawable.
- requestWithdrawal(shares) escrows shares, aggregates userEpochShares[settlementEpoch][caller], and emits both requestEpoch=N and settlementEpoch=N+1. It works while paused. Ordinary transfers to the vault are disabled; no separate share approval or transfer is required.
- Only operator() can settleEpoch(epochId), after getCurrentEpoch()>epochId. Settlement burns queued shares, fixes a performance-fee-adjusted settlementNav, and reserves settledUnclaimedAssets. Time alone never settles anything.
- claimWithdrawal(epochId) pays the caller and clears the entire owner/epoch claim. It applies the shortfall index to settled NAV, floors each integer calculation, deducts the 50-bps withdrawal fee, and accrues that fee in the vault rather than immediately paying the operator. The idle-liquidity check requires gross assets plus already accrued fees. WithdrawalClaimed.assets is the NET payout.
- The previous implementation has the same request/claim signatures, burns at settlement, and reserves liabilities, but locks the owner's whole balance after self-deposits, lacks haircuts/accrued withdrawal fees and immediately transfers the exit fee to operator(). Both versions permit withdrawals while paused. The much older d424 implementation is historical background only, not a certified execution target.

## Adapter and persistence

1. Add verified full ABI files for the current and canonical-fork implementations under eth_defi/abi/atoma, with a README recording proxy/implementation addresses, verification URLs, retrieval date, hashes and tested blocks. Retain the existing event-only ABI for discovery compatibility. Bind through eth_defi.abi helpers. Add block-aware Atoma readers for epochs, owner claims, locks, minimum deposit and fee/shortfall values; use TokenDetails for unit conversion.
2. Add AtomaDepositManager, AtomaRedemptionRequest and dataclass(slots=True) AtomaRedemptionTicket in eth_defi/erc_4626/vault_protocol/atoma/deposit_redeem.py. Override AtomaVault.get_deposit_manager and disable generic-manager fallback. Route execution only for chain 42161 and the two reviewed addresses; preflight the implementation at the operation's pinned block and reject unreviewed upgrades with a typed unsupported-version error. Certify execution only for the current 0x9161 implementation. Retain the older ABI for canonical-fork read compatibility and historical receipt decoding, not legacy execution certification. Do not guess versions from failed getter calls. Gate both transaction builders and claim operations, and retain original request evidence across upgrades; an unreviewed upgrade requires reconciliation, not automatic resubmission.
3. Deposits: preserve standard manager approval-target and analysis interfaces, call check_deposit_whitelist, accept exactly one positive decimal/raw amount, require receiver=owner for this execution adapter, enforce the block-aware minimum, maxDeposit and token balance, then build deposit(assets,owner). Keep approval separate, using the declared spender. Parse the actual matching Deposit event and minted balance; estimates never become executed holdings. Admission is permissionless for these verified implementations, while pause/cap availability is dynamic.
4. Redemptions: require exactly one positive share input and to=owner; the EOA/SimpleVault/Safe represented by owner must be the actual contract caller. Preflight balance and the current implementation's per-deposit unlocked shares, not maxRedeem/maxWithdraw (both intentionally zero). Read current epoch and reject another request if the same owner's next settlement epoch already has shares. Different settlement epochs may coexist. Build only requestWithdrawal(raw_shares).
5. Parse exactly one WithdrawalRequested from the expected vault's successful receipt; validate owner, raw shares, the emitted request-to-settlement epoch relationship, transaction identity and canonical request block. Persist the actual mined epochs even when they differ from preflight; a boundary crossing is not a reason to discard a mined request. Store base ticket fields plus chain ID, request epoch, settlement epoch, request block number/hash/log index, observed implementation, preflight implementation, reconciliation flag, request-part provenance and schema version. get_request_id returns settlement epoch; uniqueness is (chain,vault,owner,settlement epoch), not epoch alone. Serialize raw share quantities as decimal strings, hashes as hex, and any timestamps as naive UTC ISO strings. Reconstruction is offline and validates structure and manager identity before use.
6. Prevent claim misattribution: before claim construction require the onchain owner/epoch share aggregate to equal the ticket. Same-epoch out-of-band top-ups or concurrent requests mark the ticket as needing reconciliation and prevent ordinary claiming, without discarding successful request evidence. Add reconcile_redemption_ticket(ticket, hypersync_client): fetch all canonical WithdrawalRequested events for that owner/epoch, require indexed coverage through the pinned head and their sum to equal the onchain aggregate, and return one superseding aggregate ticket with each contributing tx/log/share amount and superseded ticket identity. If indexing lags, retain the pending ticket and defer. The caller must atomically replace all component tickets before broadcasting the aggregate claim. Analysis exposes the component contributions and aggregate payout; no component ticket may claim or credit that payout independently. Unattributed external requests are reported explicitly, never assigned to an existing trade. The caller must serialise submissions per owner/epoch and persist transaction hashes before waiting; contract state and receipts resolve a crash after broadcast.
7. Status: positive owner/epoch shares plus unsettled epoch => pending; settled => claimable; zero => none. claimable describes settlement, not guaranteed liquidity. can_finish_redeem also checks exact current claim simulation from owner, including accrued-fee liquidity and shortfall arithmetic. Expected InsufficientIdle returns false/typed unavailable; RPC and unknown errors propagate. finish_redemption repeats validation and returns claimWithdrawal(epoch). No cancellation/reclaim exists; do not advertise one. A status of none never proves success without a matching claim receipt.
8. Provide a ticket-specific epoch-end reader using getEpochEndTime(settlement_epoch). get_redemption_delay_over(owner) returns the current deposit-lock epoch end when locked shares remain, otherwise None; it does not prohibit withdrawing older unlocked shares. estimate_redemption_delay uses getEpochEndTime(current_epoch+1) minus the pinned block timestamp as the nominal earliest settlement eligibility, not an SLA. Set withdrawal metadata min_period=None and max_period=None, with epoch classification and the same separate non-binding estimate; exact ticket timing comes from its settlement epoch. Do not use the existing seven-day read-failure fallback in execution decisions. Implement fetch_pending_redemption_epochs(owner, block_identifier) by batching userEpochShares for epochs 0 through current_epoch+1 with the repository's chunked Multicall reader. is_redemption_in_progress(owner) is any positive returned amount. This bounded owner-wide diagnostic works after restart and on local forks; ordinary polling uses O(1) ticket reads. Do not return false on failed batches or use an incomplete history window. Shared caller inspection found no current executor usage of this owner-wide hook, but implement its bool contract rather than introducing a new capability flag.
9. Choose receipt decoding by the verified implementation at the receipt block and record it in the ticket/analysis. Compare to the operation's preflight version; version changes or intra-block upgrade ambiguity retain raw receipt evidence and trigger reconciliation rather than automatic retry. Both reviewed ABIs have identical WithdrawalRequested/WithdrawalClaimed signatures, indexed user fields and InsufficientIdle() error; test their selectors/topics explicitly. In BOTH versions WithdrawalClaimed.assets is net. Historical old-version analysis expects the separate operator fee transfer; current analysis expects fee accrual, not that transfer. Override analyse_redemption: validate successful receipt, emitter, user, epoch and exact ticket shares against WithdrawalClaimed; use its net assets and fee as realised evidence, not convertToAssets or estimated NAV. Verify matching denomination-token transfer evidence and balance deltas in lifecycle tests. Return an Atoma-specific DepositRedeemEventAnalysis subclass carrying gross assets and exit fee, allowing a verified zero net payout after total loss/rounding (the shared base currently asserts positive denomination_amount), and providing correct success semantics. Failed receipts or unmatched logs return DepositRedeemEventFailure with protocol/phase context. Do not subtract the exit fee twice or re-charge performance fees already embedded in settlementNav.
10. Implement fetch_vault_flow_events with the existing Hypersync wrappers for WithdrawalRequested and bounded owner/epoch claim recovery. Return event-derived discovery hints, not assertions of present state; deduplicate by transaction/log identity, reconcile against current owner/epoch shares and claim receipts, and send multi-request epochs through the explicit aggregate reconciliation path. Implement fetch_completed_redemption_tx_hash for recovery after a claim mined before persistence. Use supplied ranges, preserve timestamps from indexed data, and use the shared timestamp cache if bulk timestamps are needed. Never use eth_getLogs. No settlement DuckDB integration or schema change is required in this first adapter.

## Guard, settlement and consumer boundary

- Add exact requestWithdrawal(uint256) and claimWithdrawal(uint256) selector handling in GuardV0Base.sol, decoding the full one-word payload. Neither accepts an arbitrary owner/recipient: the guarded custody contract is the caller. Add whitelistAtoma(vault,notes), permitting only deposit, request, claim and the required denomination-token approval/asset surface; register the share token as an allowed asset without granting its transfer/approval selectors. Emit the existing ERC4626Approved event for configuration-scanner compatibility. Do not grant operator settlement, capital movement, upgrade, fee collection, generic target bypass, ordinary redeem/withdraw or share transfers. Preserve existing non-Atoma whitelist behaviour.
- Wire the specialised whitelist into Lagoon's ERC-4626 configuration loop and deposit_probe configuration; select it instead of (never in addition to) whitelistERC4626, and test normal deployment configuration rather than only direct test whitelisting. Check new selector collisions against all existing dispatcher constants. Rebuild Guard and TradingStrategyModule artefacts with make guard safe-integration; check both deployed-bytecode sizes against the 24,576-byte limit following docs/README-contract-size.md, retaining the existing compiler pipeline. Existing deployed modules need a compatible deployment/configuration before using the new route; this task does not deploy them.
- Implement force_settle only on verified Anvil: for a ticket, advance to the contract-computed settlement epoch end, resolve operator() from fork state, impersonate that exact actor, call settleEpoch, verify the exact ticket's transition, and stop impersonation in finally. None returns the synchronous no-op; already-settled tickets are idempotent. Allowed fork interventions are time advancement, impersonation and native-gas funding of the verified operator/USDC holder; report each. Never write protocol/token storage directly, fake roles, change NAV, inject vault liquidity implicitly or call a live operator. settleEpoch has no earlier-epoch ordering requirement; it settles every user's requests in the selected epoch, so document and verify those shared epoch effects. Unsupported simulation states produce UnsupportedVaultSimulation; liquidity remains a distinct claimability check. Report all transactions and interventions.
- Publish sync-deposit/async-redemption capability and supports_anvil_settlement only after the guarded current-version lifecycle passes for each reviewed deployment. The static capability belongs to the exact supported addresses/class; version validation lives in the manager's execution preflight, and static metadata is not a claim that a future proxy upgrade is supported. Keep unknown addresses/unreviewed versions unavailable for execution. Capability is static integration evidence, not a current liquidity guarantee.
- Consumer handoff: persist requests and claims idempotently; track queued shares separately from transferable share balance, then settlement claims separately from active share NAV. Never count escrow shares twice or treat burned shares as a realised cash payout. A settled claim can still be haircut or illiquid. Recognise cash only from the validated net payout. External trade-executor accounting, backtest epoch reconstruction and funded live verification remain explicit follow-up work. The current executor may assume positive realised amounts; zero-payout and superseding aggregate tickets must be integrated before consumer activation. Record deposit estimate versus actual minted shares; the native deposit has no minimum-shares argument, so this route cannot enforce a protocol-level slippage bound.

## Test plan and acceptance

- Unit tests: calldata and selectors; amount/receiver/minimum/cap checks; version dispatch and unknown upgrade refusal; current per-deposit locks and older receipt decoding; pause permitting request/claim; duplicate same-epoch protection; concurrent epochs; epoch schedule changes and preflight/inclusion boundary crossings; aggregate reconciliation, indexer lag, atomic ticket supersession and double-credit rejection; receipt emitter/owner/share/epoch mismatches; failed/absent receipts; serialization of large integers; wrong-chain/vault tickets; restart after request/claim broadcast; claim replay; out-of-band aggregation; pending/settled/illiquid/claimed states; haircut and fee rounding, zero payout, and no double fee charging. Keep the existing claim-only discovery count semantics.
- Real fork tests for BOTH deployments: use anvil_fork_pool, snapshots per test, fixed blocks and matching xdist groups. Canonical block 487039644 covers previous-version readers/historical analysis and generic Guard policy, not execution certification. Add a narrow protocol-version exception at 519150162 (group fork:arbitrum:atoma:519150162) for current share locks, haircuts and fee accrual; record why the canonical block cannot exercise those semantics. Warm that exact cache and shut Anvil down gracefully; do not bump the global chain constant or use latest.
- For each deployment at current block 519150162 run guarded approval => 100-USDC deposit => lock expiry => request => serialized ticket/reconstruction => epoch end => verified operator settlement => guarded claim. Execute from a delegated asset manager distinct from governance to avoid Guard bypass. Assert exact fixed-block shares, owner/vault/fee balances, pending amounts, burned shares/liabilities, emitted payout/fee, and exhausted ticket state. Derive and record exact numerical expectations during implementation. Transfer funding from an impersonated real USDC holder on Anvil; keep any artificial liquidity experiment separate from the natural lifecycle evidence.
- Add Safe/TradingStrategyModule coverage for both vaults at the current-version fork, using session fixtures and snapshot isolation. Confirm the Safe owns the shares and receives net USDC; an EOA operator/asset manager must not receive the payout. Confirm specialised production whitelist selection.
- Guard negatives: unapproved vault, sender, token/spender and deposit receiver; malformed calldata; unsupported selectors; direct redeem/withdraw; settlement/admin/capital/fee calls; Safe execution via disallowed delegatecall. Test rejection before the target executes. Generic policy tests stay on the shared canonical fork.
- Target current fork edge cases with actual authorised fork-only operations: top-up leaves older shares unlocked; paused exits; settlement without sufficient idle funds; fee accrual and collection accounting; a controlled haircut via the verified owner path in an isolated test, including zero-value settlement if executable. Use synthetic receipt fixtures for malformed/zero-payout analysis branches and small MockAtomaVault contracts under the existing Guard test-contract project for otherwise unreachable request/fee/haircut branches; compile them with the repository toolchain, source-link each modelled rule, and label this as mock evidence. Do not compile or vendor a complete Atoma implementation.
- Add a bounded credential-backed real RPC/ABI read test and real Hypersync request/claim query using supplied JSON_RPC_ARBITRUM and HYPERSYNC_API_KEY. Record exact commands, date, tested blocks/provider redacted, pass/fail and fork/mock/live-read distinction. A mocked response alone is not integration evidence.
