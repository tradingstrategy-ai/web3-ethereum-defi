# Reduce vault scan cycle time

Implementation plan for [issue #1808](https://github.com/tradingstrategy-ai/web3-ethereum-defi/issues/1808). The scanner has 60 minutes for collection **and** publication. Implement and measure the native merge change first, then reduce cleaning work. Keep the existing full builders as the reference and recovery path.

## Implementation status

The numbered sections below record the proposed design and acceptance checks. The implemented scanner discovers dirty vaults by comparing committed inputs with their last published fingerprints. It tracks native revisions in the raw Parquet footer and uses one pending marker for the cycle. The cleaner uses a single checkpoint covering all three outputs. Writer-side revision counters, per-consumer queues and per-vault tombstones were design options. The [scanner guide](../../scripts/erc-4626/README-vault-scripts.md#incremental-vault-price-publication) describes the implemented settings and recovery behaviour. Local replay measurements are reported below. Production timings and the archive collision audit are outstanding.

## Production baseline

Six completed runs on 22 November 2026 UTC at revision `6acffcd33` gave the following independent ranges. Use whole-run observations when comparing totals.

| Stage | Wall-clock minutes |
| --- | ---: |
| Native price merge | 12.4–14.4 |
| Stablecoin and crypto cleaning | 15.9–20.6 |
| Listing generation and upload | 9.8–10.8 |
| Remaining metrics and exports | 19.9–24.9 |
| Total post-processing | 58.5–69.3 |

| Cycle | Work due | Start / post-processing start / end (UTC) | Post-processing | Whole cycle |
| --- | --- | --- | ---: | ---: |
| 10 | Base and Ink, zero native protocols | 06:30:29 / 06:44:23 / 07:52:14 | 67.8 min | 81.8 min |
| 12 | Arbitrum and six native protocols | 08:52:14 / 09:31:10 / 10:29:37 | 58.5 min | 97.4 min |

Cycle 10 rebuilt 2,336,885 HyperCore rows and rewrote approximately 24.8 million combined rows. Saving the entire native merge would still leave about 68–69 minutes. Reading 12.16 million stablecoin rows took 8–10 seconds, while transforms took 593–810 seconds, including 173–228 seconds of EVM outlier repair. The listing selected roughly 6,700 vaults for recalculation.

Cycle 12 spent 38.9 minutes collecting. Even the observed minimum listing and remaining export times together add 29.7 minutes, putting that workload above budget before merging or cleaning. Evaluate the EVM-only cycle against 60 minutes and quantify the remaining gap for changed-native cycles. Instrument individual exports from the first rollout. Measure how often each native revision changes and what fraction of historical rows belong to dirty vaults before choosing the targeted-cleaning crossover.

## 1. Make native materialisation depend on its inputs

- In `eth_defi/vault/scan_all_chains.py`, keep collection schedules and success callbacks independent of publication. At the start of `merge_native_protocols()` in `eth_defi/vault/post_processing.py`, compare every enabled scope with its last published revision **before** opening full histories or loading metric snapshots. Extend the loop's “no scans due” branch to service outstanding publication work without forcing a collector run.
- Give each native store a durable revision per replaceable scope. Advance it in the source transaction for inserts, historical updates and deletions affecting prices, permissions, inventory or perp snapshots. Include a store incarnation for replacement/restoration, both HyperCore daily and high-frequency inputs, and explicit transformation/schema and capability-registry versions. Inventory all writers including numbered migrations. Require explicit invalidation for restores or writers without revision support, falling back to rebuilding an untracked scope. Counts, maximum timestamps and collector success cannot detect an old correction.
- Keep Lighter Ethereum and Robinhood separate by deployment address namespace on chain 9998. Filter price and metric reads and replacements accordingly. Preserve the legacy 9996 removal condition. Retain existing merge-with-history semantics for ApeX, Derive v3 and scoped Neutral Trade, including unrelated Solana rows. Define deletion ownership explicitly for these sources. An authoritative empty scope can remove its owned rows. A missing store or failed read retains the last good data and leaves work pending.
- Batch all changed scopes through the existing PyArrow writer once. Preserve schema metadata and untouched scopes. When all inputs and required outputs match, call neither the builders nor the writer. Account separately for HyperCore's metadata repair and permission-history export so a missing side output can be repaired independently. A missing combined file also needs its EVM contents restored or rebuilt before it can be published as complete.
- Before publishing a raw or cleaned replacement, check ownership, keys and row accounting. Require non-null keys and verify that each candidate key occurs once, using canonical `(chain, address, timestamp)` for raw prices and `(id, timestamp)` for cleaned prices. Reject overlapping replacement scopes and duplicate keys within an incoming scope. For append-style native histories, a fresh row may replace one stored row with the same canonical key. Verify that the candidate contains exactly the retained and replacement rows, that retained keys and values survive, and that each removed key belongs to an authorised replacement or deletion. Check counts by scope as well as the combined total, since losing one row and adding a duplicate can leave counts unchanged. Account for expected schema alignment when comparing retained values.
- Before enabling publication validation, audit existing raw and cleaned Parquet for canonical-key collisions. If the audit finds collisions, resolve them in a numbered migration before enabling the check. Collapse equal rows after canonicalisation and report their keys and counts. Resolve conflicting values from the authoritative input or an explicitly verified correction, then rebuild the affected derivatives. Preserve the pre-repair artefacts for comparison.
- If an input read, transformation, validation or write fails, leave the last verified file and its applied revision intact for the failed scope. Report the failure and keep its work pending. A successful sibling scope may still publish if the candidate validates and retains every row of the failed scope. Before advancing any checkpoint, verify the staged Parquet and atomically replace the destination. Exercise failed reads, invalid candidates and failed renames.
- Persist the applied revision vector beside scanner state, under the existing writer exclusion. Bind it to the native contents of the output (for example, native revision metadata in the Parquet footer preserved by every EVM-only rewrite). Avoid using the mtime of the shared file as the native identity. Compare the actual output and checkpoint, including side outputs. Bootstrap conservatively on missing, incompatible or mismatched state. Publish verified temporary files by atomic rename, then acknowledge only the captured revisions of successful scopes. Replaying a crash between rename and acknowledgement must be idempotent.

## 2. Recalculate the complete histories of affected vaults

- Carry `rows_written_by_vault` from `eth_defi/vault/historical.py` through `scan_prices_for_chain()`, `scan_chain()` and retries using canonical `VaultSpec` identities. Preserve existing aggregate counters. Capture removals from the pre-write selection as well as new rows. For native replacements enqueue the union of old and new owned vaults. Use the cleaner's canonical identity rules for synthetic native addresses and keep chain IDs in all joins.
- Normalise EVM addresses before comparing or joining raw rows, dirty IDs, catalogue records, settlements and existing cleaned keys. Include legacy checksummed addresses already on disk. A lowercase filter applied to legacy raw text can miss the history before the cleaner runs. Use the repository's chain-specific `VaultSpec` rules for native keys, including decoding case-sensitive Solana base58 before converting it to the storage key. Cover identical EVM address text on two chains and mixed-case aliases within one chain. Surface historic canonical collisions explicitly and require a documented reconciliation for conflicting rows before publishing.
- At metadata and settlement writers, collect IDs whose cleaner inputs actually changed, including denomination moves, eligibility, removals and corrected settlement dates. Account for other vaults affected by shared metadata such as name disambiguation. Invalidate the whole affected family for changes whose impact cannot be bounded. Distinguish an explicitly empty change set from unknown scope.
- Persist pending IDs **before** a non-transactional file replacement, or in the source transaction where supported. A failed write can then cause harmless extra cleaning. Hold the writer lock through preparing and publishing, union concurrent workers' changes without lost updates, and track the input generation each consumer processed. On restart replay from committed sources. An acknowledgement must never erase later changes to the same vault. Keep skip flags, failed collectors with partial commits and failed downstream stages from discarding pending work.
- Extend `replace_cleaned_vault_histories()` in `eth_defi/research/wrangle_vault_prices.py`. Reuse the full builder's selection, full-catalogue metadata, settlement annotation, native suppression, capability registry, denomination and daily sampling rules. Select each affected vault's entire raw history using grouped chain/address membership or dataset push-down. The existing per-ID comparison in every batch needs benchmarking for large sets. Reuse sorted stream-copy and verified atomic replacement. Preserve strict defaults for existing migration callers. Support typed empty replacements for confirmed deletions and family exits, including deletion-only batches. Keep the full cleaner's protection against accidental empty public output.
- Cover the stablecoin hourly output, its daily sidecar and the isolated crypto daily bundle. Route an ID to both former and current families when classification changes. Use separate durable acknowledgements or a generation manifest so a crash between outputs cannot leave an old daily sidecar eligible for a new hourly generation. Retain the hourly fallback and crypto failure isolation. When inputs are known unchanged and outputs valid, skip each clean. Bootstrap, unknown lineage or changed transform versions use the full builder. Compare targeted and full costs at representative dirty-set sizes before choosing a crossover.

## 3. Measure downstream work and verify parity

Keep current listing, rolling-window, exchange-rate, ranking and export schedules for the initial change. Record why a downstream stage ran, including elapsed-time expiry, changed external inputs and outstanding upload retries. A ranking input change requires ranking the whole eligible population. Price dirtiness alone cannot determine listing or export freshness.

Extend focused scanner, post-processing and cleaner tests using local Parquet and DuckDB fixtures. Run the real scheduler-to-publication path for the no-op and retry cases. For parity, start two copies from the same snapshot, apply the same mutations, run incremental processing on one and a forced full rebuild on the other with the same clock and inputs.

| Case | Required observation |
| --- | --- |
| EVM writes with unchanged native inputs | Zero native builds, snapshot loads and native-stage raw writes. EVM rows survive. |
| One native scope changes | One batch write. Only that scope is built. Other scope histories, including Lighter's sibling, survive. Exercise permission-only, perp-only and historical same-count corrections. |
| New price, old correction, last-row deletion, settlement-only change, denomination move | Compare sorted keys, timestamps, prices, returns, outlier repairs, settlement fields, schema metadata and daily values in all affected products against full output. Check retained rows, key uniqueness and order. |
| Publication interrupted | Inject failure before raw rename, after rename before checkpoint, and between hourly, daily and crypto writes. Restart with no collector due. Pending work converges; failed uploads can retry independently. |
| Address case and invalid merge | The known legacy observation and its expected values appear under one canonical cleaned ID at the expected hourly and daily keys. The same address on another chain survives. A fresh native correction of an existing canonical key leaves one row. A conflicting duplicate or an unexpected deletion fails validation and leaves the previous file and revision available for retry. |
| Bootstrap, restore and migration | Remove checkpoint or output, change transform version and repair an old source row. Verify rebuild scope, retained history and next-tick no-op. |

3. Require the log to show targeted cleaning for the expected dirty set and no full-clean fallback. Choose a fixture whose dirty set fits the targeted-cleaning crossover. 4. In a fresh scratch copy, commit a HyperCore correction while its collector remains not due. Run publication again with identical inputs and require a native skip.

Run the one-chain comparison with both incremental settings unset to exercise the scanner defaults. Use a new numbered migration and run reminder if persisted production state needs repair.

The scanner defaults to revision-aware native merging and targeted cleaning. Set `INCREMENTAL_CLEANING=false` for a full clean, or `INCREMENTAL_POST_PROCESSING=false` for a full native merge and clean. The implementation compares committed per-vault fingerprints with the last published cleaning snapshot. The fingerprint comparison covers migrations and retries that bypass the scheduler's writer counters. The output checkpoint identifies the hourly, daily and crypto files together. An interrupted write or restored file triggers a full clean on recovery.

Native revision checks use the local DuckDB file and write-ahead log generations under the pipeline lock. Lighter fingerprints the committed inputs of each deployment independently and tracks when the latest daily flow becomes final. A source replacement that loses an existing vault or shortens its published time range requires a verified repair. Bump `NATIVE_MERGE_VERSION` or `CLEANER_VERSION` when changing the corresponding transform or shared policy.

#### Local implementation measurements

Three paired replays used 622,728 EVM observations across 288 vaults, plus one HyperCore observation. The comparator ran full materialisation on the implementation checkout. Both modes used the same committed input changes. The timings cover native merging and cleaning through all three local price files. Collection, listing and uploads were outside the timed section.

| Committed change | Native merge full → incremental | Cleaning full → incremental | Timed total full → incremental | Reduction in median elapsed time |
| --- | ---: | ---: | ---: | ---: |
| Base price only | 0.463 s → 0.002 s | 3.78 s → 0.71 s | 4.24 s → 0.71 s | 3.53 s (83%) |
| HyperCore price only | 0.492 s → 0.510 s | 4.10 s → 0.70 s | 4.59 s → 1.22 s | 3.37 s (73%) |

The timed totals ranged from 4.17–4.60 s full and 0.68–0.84 s incremental for the Base change, and from 4.59–4.72 s full and 1.19–1.39 s incremental for the HyperCore change. The Base replay skipped the HyperCore scope and wrote zero raw Parquet files from the native stage. The changed-native replay rebuilt one native row and rewrote the combined raw file once. Each replay recalculated one cleaned vault. All three output DataFrames matched the same-input full rebuild in each pair. Bootstrap cleaning took 3.33–4.30 s and is outside the steady-state timings.

The Base correction replaced 1,200 hourly rows and retained 596,905. Each daily output replaced 68 and retained 27,725. The HyperCore correction retained all 622,728 EVM rows in the single raw rewrite, replaced one hourly row and retained 598,104. Each daily output replaced one and retained 27,792. In both cases all three cleaned files were rewritten.

A separate scratch run used the real loop scheduler with Base collection replayed from a local fixture. The Base-only cycle completed in 2.95 s. A second tick failed at the native raw rename and retained the previous bytes. The next tick published the correction in 3.57 s with no collectors due. These measurements cover local replay only. Run the live Base test, production collision audit and production before-and-after timing to validate the deployed scanner.

## Publication and recovery details from review

- Read the source revision and data from the same snapshot. Advance revisions on effective data changes. When a native scope changes, narrow its old/new ID union using changed per-vault inputs where available. Measure the conservative union cost where precise attribution is unavailable.
- Treat the revision embedded in the verified output as authoritative for its contents. The checkpoint records completed work across dependent files. A missing checkpoint forces a rebuild. If a crash leaves the footer ahead of an existing checkpoint, replay the unacknowledged scope from source and finish its dependants. Flush temporary files and sync the containing directory after rename before acknowledging. Validate each daily derivative against its hourly generation in the crypto builder.
- Delete only with positive evidence of source ownership and committed removal, such as a tombstone or a completed authoritative inventory for that store incarnation. A newly created empty database is insufficient. Retain disabled scopes until an explicit retirement. Coalesce pending work by scope, vault and consumer, retry failed publication after due collection, and expose oldest pending age and repeated failures.
- Catalogue all combined raw writers, including numbered backfills, restores and schema repairs. They must record known identities or invalidate the affected scope before writing. Benchmark a reconciliation pass using per-vault input fingerprints for writers with unknown lineage, including the cost of hashing. Audit transforms for shared inputs and time dependencies before enabling targeted cleaning. Invalidate the relevant consumers on changes to registry data, exchange rates or time windows.
- Keep both sides of a family move pending until the products built from that generation are verified. Keep the previous complete crypto bundle available after a crypto failure. Retry uploads from the current verified generation and publish any multi-file bundle readiness marker last.
- Add multi-tick parity with an advancing clock, a change to the same ID during cleaning, an interrupted family move, a restored-empty or disabled scope, an EVM repair outside the normal scanner and a restart with collectors already due. Check both pending work and output values after recovery.
