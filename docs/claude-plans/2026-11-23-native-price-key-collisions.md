# Repair native price publication after duplicate key failures

## Incident and scope

On 23 November 2026 the six native collectors finished, then the incremental price merge introduced in [PR #1812](https://github.com/tradingstrategy-ai/web3-ethereum-defi/pull/1812) rejected the ApeX history and the combined candidate. The 14:00 UTC top-vault JSON upload used the last committed raw history. Private native price publication remained pending across three attempts. Repeated retries cost almost four minutes each.

The deployed commit was `bc2d1df3c`. The 10:24 UTC raw Parquet contained 24,881,194 rows. Two findings from the read-only audit determine the repair:

| Population | Evidence | Required outcome |
| --- | --- | --- |
| ApeX, synthetic chain 9995 | 109,361 excess rows across 686 vaults. Each duplicated millisecond key matched one microsecond DuckDB observation. The source had zero collisions at millisecond precision. | Reconcile one stored observation per key and preserve the price and available enrichment. |
| EVM history | 1,040 pairs on Arbitrum, Avalanche, BNB Chain, Robinhood and Base. Every pair had distinct block numbers at the same vault address and second. | Preserve both block observations in every pair and every other retained row. |

For example, one ApeX ranking observation at 14:17:00.907127 UTC on 24 July was stored at 14:17:00.907. The old merge compared the full source timestamp against the stored millisecond, retained both, then cast both to the same millisecond. Use these counts for the inspected snapshot. Recompute them from frozen inputs for a later deployment.

## Changes to the merge

1. In the [history merge and partition writer](../../eth_defi/vault/post_processing.py), construct ApeX identity from the canonical address and timestamp at the Arrow target column's precision (currently milliseconds). Use that key for source uniqueness, persisted history matching and fresh corrections, including first publication, an empty existing partition and full-mode fallback. Keep source-collision checks active even when incremental revision tracking is disabled. Keep the precise source timestamp available for diagnostics and time-sensitive metric joins. Derive the comparison key using the same millisecond truncation as the schema cast. Test a positive UTC timestamp ending in .999500 and discard temporary comparison columns before constructing the Arrow output. Report a bounded sample of colliding source keys and their original timestamps and fail the scope before writing if two source observations map to one key.
2. Validate the rows the native writer owns after Arrow schema alignment. Check nulls, uniqueness, replacement ownership and existing scope coverage. Use the same canonical address rules as the writer, including case-sensitive Solana identities and Lighter's deployment namespaces. The retained side and replacement side must be disjoint by the same ownership predicate used for removal. Preserve the combined table's established sort order and row accounting. Move uniqueness validation off the retained EVM history. Reuse the existing sort or check only the changed keys with a vectorised operation. Avoid a second global sort, whole-file group-by or additional Parquet read.
3. Preserve the existing revision checks, including Lighter's scoped database reads. Once a scope is known to be unchanged, skip its history builder, metric attachment and raw rewrite. Keep source conflict checks on the changed ApeX input and combine them with existing validation where possible. Keep retryable errors visible and advance the publication checkpoint only after the normal successful stages.

## One-time repair

Add the next unused numbered migration under [migration/scripts](../../migration/scripts). Use the migration runner's preview, locking, backup and journal conventions. Freeze a matching set of raw Parquet, ApeX DuckDB and enrichment inputs for the rehearsal. The migration must fail closed on missing, unreadable or incompatible required data.

Inventory repeated ApeX keys at millisecond precision. Record counts and example identities. The audited groups all contained two rows. Compare typed values with null- and NaN-aware equality. Apply these rules in order:

| Stored rows at the key | Source at the same key | Action |
| --- | --- | --- |
| One row | Any | Preserve the stored row during migration, including raw-only history. |
| More than two rows, or a pair differs outside the three enrichment fields below | Any | Abort staging and report the key, group size and differing fields for explicit review. |
| Pair | Multiple source rows | Abort and report the original source timestamps. |
| Identical pair | Zero or one source row | Retain one identical stored row. |
| Pair differs only in enrichment | Zero source rows | Abort and report the unresolved key. |
| Pair differs only in enrichment | One source row | Rebuild the three enrichment fields against the frozen metrics inputs. Keep the pair's agreed core values. |

A later change in the source price is a normal fresh correction. The migration keeps the agreed stored price, and the next successful ApeX merge applies the correction. Rehearse this path with an already-matching source revision: if a correction is outstanding, invalidate only the ApeX revision so it will be processed.

Of the duplicate pairs audited, 108,981 differed in at least one of `perp_metrics_observed_at`, `perp_quote_asset` and `perp_position_data_status`. Use the [raw metrics attachment logic](../../eth_defi/perp_dex/parquet.py) and each affected account’s full timeline so only its true latest price receives the latest-price overlay. Use the original source observation and snapshot timestamps throughout replay. Preserve cleaned-product finalisation for the downstream cleaner. Update only the affected keys. If provenance cannot resolve the enrichment, abort and report the key for review. Preserve all other columns, extension fields, schema and metadata, including unrelated native revisions.

- Stage one replacement on the same filesystem. Before atomic rename, verify that every original distinct ApeX key survives exactly once, the row-count delta equals the proven excess and the multiset of all out-of-scope rows and values is identical. Use bounded batches and a disk-backed comparison where needed to prove multiset equality across row-group boundaries. Preserve all EVM blocks, old native history and reader state. Check free space for staging and backup. Applying twice, including after a crash between rename and journal commit, must be safe. On the second pass with no duplicates, verify the postcondition and skip the rewrite. Keep repair scans and full-history comparisons out of recurring cycles. On the copy, seed the pre-repair cleaning checkpoint. Prove the changed raw fingerprints rebuild all affected histories and exports even with unchanged source revisions, and that the second tick skips them. If this fails, invalidate only the affected cleaning state as part of the migration.

## Verification and performance gate

Extend the existing [native batch merge tests](../../tests/erc_4626/test_native_protocol_batch_merge.py) and [post-processing tests](../../tests/erc_4626/test_post_processing.py). Cover a microsecond replay across two writes, a real same-millisecond source collision, a source correction, retained source-missing history, two EVM blocks in one second, scoped native ownership and failure before publication. Exercise the migration in preview, apply, no-op rerun and conflicting-source cases. Include the latest-price overlay and an independently valued retained column.

Use the measurements in the [original performance plan](2026-11-22-incremental-vault-post-processing.md) as context. The following checks are implementation acceptance criteria:

- Assert operation counts for an unchanged tick, an EVM-only tick, a changed ApeX scope, a mixed native merge, and an idle retry. Unchanged native inputs must keep their existing revision-only path, with zero native history rebuilds or native-triggered raw writes. A successful changed batch gets at most the existing single raw rewrite. Compare Parquet body reads, source opens, global sorts, rows passed to validation and writes against the control. Include downstream cleaning in the comparison.
- Benchmark on isolated production-sized copies. The deployed code fails on the incident file, so its failed run cannot time successful publication. For paired timings, derive a benchmark-only control input accepted by both builds, by repairing its ApeX pairs, truncating timestamps in its copied ApeX source and removing one member of each of the 1,040 same-second EVM pairs on the timing fixture only. Record these deltas and check both builds complete. Reset raw data, source revisions, paths, cleaning state and pending marker from the same pristine fixture before each run. Warm each workload once under consistent conditions and exclude warm-up. Run both builds with identical source revisions, worker counts, cache conditions and cleaning state. Separately replay the unmodified incident copy through migration and the candidate to prove fidelity and recovery. Include a replay using the original microsecond source alongside the common timing fixture. Record its ApeX stage time, allocations and row counts to catch costs hidden by pre-truncating the fixture. Route benchmark exports to an isolated destination.
- Alternate baseline and candidate order for at least five paired runs per workload. Record paired wall times for the merge, cleaning and complete tick, together with peak RSS and bytes read/written. Record the median and range for each workload separately. Before testing the candidate, measure five baseline-versus-baseline pairs. For wall time and peak RSS separately, set the allowed noise to the median absolute paired percentage difference, capped at 2%. Gate each workload and its measured stages on a candidate median paired increase within that allowance and peak RSS below the production container limit. Require zero additional raw-file scans, whole-table sorts or rewrites per workload. If a gate is exceeded or the baseline is noisier than 2%, repeat once with five more pairs under controlled load. Withhold sign-off on a persistent failure or inconclusive result. Record headroom against the scanner’s 60-minute schedule. Budget 60 minutes for the first post-repair tick with the actual dirty histories. If the rehearsal exceeds that budget, explicitly schedule a longer recovery window before rollout. Measure migration time, memory and disk separately so the operator can size the maintenance window.

## Production rollout and recovery

Build the reviewed, stamped image. Follow the [production runbook](../../.claude/docs/migration-scripts.md#production-runbook) for stopping all writers, acquiring locks, previewing and applying the migration, and recreating the services. Include a migration reminder in the implementation PR. Keep the scanner stopped from the production preview through successful apply so the candidate first reads repaired history. Repeat the preview against the quiesced production files, check the inventory against staged results, and abort on new unresolved conflicts. Keep the backup and journal through verification and leave the publication marker under the scheduler’s control.

On restart, verify that the scanner runs the stamped commit, all six pending native scopes complete, cleaning and private exports use the new raw data, and the pending marker clears following successful publication. Confirm the next unchanged tick skips native work. If a future ApeX source collision occurs, report both precise observations, allow independent raw scopes to commit, keep ApeX pending and retain the private publication guard. Resolve it from the source before retrying. If validation fails, keep the prior valid output and inspect the journal. For a rollback after commit, stop writers and restore matching data, checkpoints, journal and image from the pre-apply backup. Restoring the incident snapshot restores the duplicates, so publication then requires a corrected repair and replay.
