## Onchain reads and limitations

Live reads at block 510299362 confirmed both LP tokens have 18 decimals and readable `totalSupply()`. Both `asset()` and `totalAssets()` reverted. At block 510299723, both managers returned `removeLiquidityCooldown() = 604800`, `minimumLiquidityAmount() = 10000000`, and `inPrivateMode() = false`. These are mutable parameters.

Token `balanceOf(staking_contract)` supplies the staked quantity; it is not a USD valuation. The DefiLlama TVL adapter reads precisely this quantity for each pool.

Verified source was fetched through Etherscan v2 for [AmlpManager](https://arbiscan.io/address/0x98a6aEE58699e4f4E13D8d8d0800e4e9cbBcf8dD#code) and [AhlpManager](https://arbiscan.io/address/0xc5F9d4b9f68CAAA869317Baa09a233b22940bd9f#code). Neither was reported as a proxy. Both expose pending `userDeposits(address)` and `userWithdraws(address)` and signature-gated withdrawal methods.

Their authorised handlers call `batchProcessAMLP()` / `batchProcessAHLP()` with externally supplied `TVL`, mint amounts and redemption amounts. Deposit share calculation uses the supplied TVL and pre-batch token supply. `AddLiquidity` / `RemoveLiquidity` events publish TVL and actual token amounts. Neither manager exposes a current NAV getter or independently computes trading PnL. Exchange vault source was not verified in the explorer response, so its internal accounting was not established.

Historical execution ratios can be decoded from both subscription and redemption amounts. The implemented canonical series uses subscriptions only: redemptions accept handler-supplied amounts without enforcing the subscription pricing formula and remain diagnostics. They are not a continuous, independently verified NAV series. Use Hypersync for historical events, not JSON-RPC `eth_getLogs`.

The production frontend's embedded AMLP manager ABI is stale: it includes `REMOVE_LIQUIDITY_COOLDOWN()`, which reverted on the deployed contract. The verified ABI exposes `removeLiquidityCooldown()` instead. Prefer the verified ABI.

## Public API

Base URL: `https://prod-gateway.antarctic.exchange`.

| Data | AMLP endpoint | HTTP method |
| --- | --- | --- |
| Current price, TVL, supply, APR | `/lp-gambling/pub/amlp/detail/pool/info` | GET |
| Contract addresses | `/lp-gambling/pub/amlp/detail/contract/info?chainName=ARBITRUM` | GET |
| Price, TVL and return history | `/lp-gambling/pub/amlp/detail/apy-chart/v2` | POST |
| Risk metrics | `/lp-gambling/pub/amlp/statistics/riskMetrics` | GET |

For AHLP replace `/lp-gambling/` with `/lp-hedging/` and `/amlp/` with `/ahlp/`. Current pool info and contract configuration were tested successfully for both pools without authentication. The AMLP risk metrics endpoint also returned a successful response.

History requests were tested successfully for both pools with form body `timeType=3` and content type `application/x-www-form-urlencoded`. The frontend defines `1` as day, `2` as week, `3` as month. The month response contained 44 rows, from 2026-08-17 16:00 UTC to 2026-09-29 16:00 UTC; the frontend drops the first 13 rows in some calculations. Timestamps are Unix milliseconds. Arbitrary start/end date support has not been established.

Use a decimal-preserving JSON parser for financial values: the backend returns high precision JSON numbers, alongside some string quantities. Check application `code == 0` and the presence of `data`, rather than HTTP status alone. Incorrect chain casing returned HTTP 200 and success code with no data.

The current responses include `amlpPrice` / `ahlpPrice`, `tvl`, `lptTotal`, `stakeTotal`, `baseApr`, `boostApr` and nullable `apy`. Observed snapshot:

| Pool | Reported LP price | Reported TVL | Reported base APR |
| --- | --- | --- | --- |
| AMLP | $0.89693924 | $5,368,794.45 | 2.45% |
| AHLP | $1.02059650 | $2,813,065.39 | 1.60% |

These are backend-reported values, not independently calculated onchain asset valuations. Observed TVL approximately equals price times `stakeTotal`, not price times all `lptTotal`; define the TVL metric explicitly when integrating.

Do not label the historical `apy` field as independently established annualised yield. Samples approximately equal `price - 1`, suggesting a cumulative return from a $1 starting value; this interpretation needs protocol confirmation. `baseApr` is separately reported. Calculate realised period returns from the price series and account separately for staking distributions.

## Implemented integration

The repository uses a protocol-specific onchain reader for subscription execution prices and reported pre-batch TVL, backed by Hypersync settlement context. It does not import API valuations. An ERC-4626-only scanner cannot obtain these historical prices; neither event ratios nor backend values establish independently calculated portfolio NAV. Public API findings above are a separate research record, not a fallback data source. See the [Antarctic integration README](../../eth_defi/erc_4626/vault_protocol/antarctic/README-Antarctic.md) for supported semantics and operator commands.

The implementation has not been deployed to production. Public API and RPC checks in this research record were manual investigation runs, not CI tests; the implementation adds separate authenticated Hypersync integration tests. A canonical contract repository, audit report and complete pool fee schedule were not established in this investigation.

## Hypersync settlement frequency investigation

On 2026-09-30, streamed all events from both deployed managers, from block 0 through Arbitrum block 510301932, using `configure_hypersync_from_env()` and `open_hypersync_stream()`. This returned 1,966 manager events. Associated event headers were preserved in the shared per-chain timestamp cache and exact coverage was checked through `fetch_exact_block_timestamps_using_hypersync_cached()`.

The rolling windows below end at 2026-09-30 09:10 UTC. Distinct settlement transactions are counted separately from events because one manager batch can emit multiple settlement events.

| Pool | All settlement events | All settlement transactions | Last 90 days: events / transactions | Last 30 days: events / transactions | Last 7 days | Latest settlement, UTC |
| --- | --- | --- | --- | --- | --- | --- |
| AMLP | 932 | 733 | 15 / 14 | 2 / 2 | 0 | 2026-09-16 14:11:25 |
| AHLP | 48 | 48 | 11 / 11 | 2 / 2 | 0 | 2026-09-10 07:04:17 |

AMLP's history starts on 2025-01-07 and contains 635 `AddLiquidity` and 297 `RemoveLiquidity` events. AHLP's starts on 2025-07-15 and contains 34 adds and 14 removals. In the last 90 days, AMLP had settlements on 11 distinct UTC dates and AHLP on six. Median gaps between observed settlement transactions in that window were 152.93 hours for AMLP and 48.57 hours for AHLP. These statistics omit the trailing gap after the last event; they do not describe a scheduled NAV publication cadence.

The latest AMLP settlement was a 101 USDT deposit receiving 112.71002884 AMLP, implying approximately 0.89610482 USDT per share, with handler-reported TVL of 6,253,637.183332 USDT. Its [transaction](https://arbiscan.io/tx/0x375492548824f0e2590f176e517f33f6848339b835c68eac57dbb3410353695c) emitted the account address and the exact raw amounts. The latest AHLP deposit was 10 USDT for 9.80618574 AHLP, implying approximately 1.01976449 USDT per share, with reported TVL of 3,182,499.724032 USDT. Its [transaction](https://arbiscan.io/tx/0xfd8f513f15d1b60b0b64b58b72cb086b6708311e2a3081d8b3a5988483397e6c) followed a removal about ten minutes earlier on the same day.

Amounts decode as USDT with six decimals and LP tokens with 18 decimals. TVL uses the USDT raw unit. The event data supports settled cash flows, execution-price samples and handler-reported TVL, alongside transaction hash, block, UTC timestamp and log index. It does not supply trading positions, independently calculated PnL, fee breakdowns or staking distributions. `PoolDeposit` and `PoolWithdraw` describe requests and must not be treated as settled price observations.

### Direct token supply changes

The sparse manager events do not represent all activity. A separate Hypersync query selected zero-address ERC-20 `Transfer` events from both LP tokens over a roughly 31-day block range, then fetched their associated transactions and all transaction logs. After filtering exact timestamps to the rolling windows above:

| Pool | Last 30 days: direct mints | Last 30 days: direct burns | Last 7 days: direct mints | Last 7 days: direct burns |
| --- | --- | --- | --- | --- |
| AMLP | 251 | 324 | 72 | 80 |
| AHLP | 51 | 74 | 9 | 19 |

These transactions call the token contracts directly with `mint(address,uint256)` or `burn(address,uint256)`, bypassing the manager settlement methods. The quantities are not evidence of profitability: they change supply without publishing a USDT exchange amount, TVL or share price. In the checked direct mint/burn transactions, the only log emitters were the LP token contracts; there were no USDT transfer logs or manager valuation events in those same transactions. This does not rule out related transfers in separate transactions or backend accounting.

The latest observed direct AMLP mint occurred at 2026-09-30 09:09:01 ([transaction](https://arbiscan.io/tx/0x07d2e9a09cc58a684b6332c05ae279b1ed7e06872a7f4e2e93d5517e3cbf201c)); the latest AHLP burn occurred at 2026-09-30 04:33:00 ([transaction](https://arbiscan.io/tx/0x6ca060f165a257e71fc87def70a5a76608fa5bf1e82f5d872ac49d7d31911e62)). Direct activity averages roughly 19 AMLP and four AHLP mint/burn transactions per day over the last 30 days, while usable onchain price observations remain sparse.

Manager subscriptions supply historical execution-price samples, with gaps of several days or weeks in the recent window. Frequent token mint/burn events cannot fill those valuation gaps. The implemented reader preserves this sparse onchain series and its last observed timestamps; it does not add daily API values or infer a price from supply changes.
