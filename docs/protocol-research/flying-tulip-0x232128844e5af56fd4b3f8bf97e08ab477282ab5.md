- Proxy: [0x232128844e5af56fd4b3f8bf97e08ab477282ab5](https://etherscan.io/address/0x232128844e5af56fd4b3f8bf97e08ab477282ab5#code).

- Product context: [ftUSD documentation](https://docs.flyingtulip.com/product-suite/ft-usd/), [22 September announcement](https://x.com/flyingtulip_/status/2102404682685501823), corroborated by the [September update](https://blog.flyingtulip.com/flying-tulip-september-update/).
- Contract development/security repository: [flyingtulipdotcom/security](https://github.com/flyingtulipdotcom/security). No public source-development repository or report-level audit for this exact implementation was established. It uses OpenZeppelin upgradeable ERC-4626 components, with Flying Tulip's own reward and withdrawal logic.
- DefiLlama: [Flying Tulip](https://defillama.com/protocol/flying-tulip); a separate ssftUSD yield-pool listing was not established.
- Fees: reviewed standard deposit/redemption code deducts no direct staking fee. Relayed session flows can charge a user-authorised relayer fee; gas and separate ftUSD mint/redemption costs remain additional. The existing integration's Ethereum 0.07% USDC conversion costs are historical reviewed configuration, not a new live-fee verification.

ssftUSD accepts six-decimal ftUSD and issues eighteen-decimal shares. Funded ftUSD rewards vest into `totalAssets()` over eight hours. Yield compounds into the redeemable share price; it is not an external FT distribution or a synthetic reinvestment curve. The documented allocation is slightly lower than sftUSD's.

Standard exits are synchronous and revert atomically if the underlying wrapper would queue them. Reward vesting is not a withdrawal lockup. `maxDeposit(0)` returns zero because the receiver is invalid and cannot establish global capacity. The old ftUSD contract-registry API omits this product, explaining why the prior sftUSD-only integration left its protocol unknown even though name matching identified the curator.
