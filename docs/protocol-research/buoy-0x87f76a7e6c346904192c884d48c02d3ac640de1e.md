# Buoy Finance preliminary integration analysis

This preliminary assessment predates the adapter. The [implemented reader](../source/vaults/buoy/index.rst) uses published onchain accounting for prices and supply.

Research date: 2026-11-14. Scope: public documentation, the deployed web
application's exported interfaces, public API reads and repository architecture.
No implementation, RPC state checks, fork transactions or production changes.

## Assessment

Buoy looks supportable as a HyperEVM tokenised trading-vault integration, with
a custom asynchronous deposit manager and a separate live valuation source.
It is neither a synchronous ERC-4626 vault nor a native Hyperliquid vault.
Discovery and data support should precede execution certification. The main
uncertainty is reliable historical and live share pricing, rather than finding
vault addresses.

## How it is connected

According to the [architecture documentation](https://docs.buoy.finance/protocol-deep-dive/architecture.md):

```text
Depositor wallet / guarded custody
  -> Router: requests, cancellation, native request fees
     -> Factory: registry and minimal-proxy vault deployment
     -> BuoyVault: ERC-20 shares, USDC custody, request accounting
        -> VaultPolicy: v3 deposit admission and limits
        <-> HyperCore account belonging to the vault
            -> spot, perpetuals, HIP-3 / HIP-4 markets

Leader's agent -> trading on HyperCore
Protocol fulfiller -> live NAV calculation, Router settlement, exit liquidity
Backend / indexer -> vault metadata, charts, live quotes
```

The vault contract itself is the share token. Shares and EVM USDC use six
decimals; share-price views use an 18-decimal scale. HyperCore USDC uses
eight decimals. The documented vaults are fixed implementation clones, while
the shared Router and Factory are upgradeable. v3 adds an external policy;
v2/v3 expose `VAULT_VERSION()`, whereas v1 does not.

Buoy's HyperCore accounts are not native Hyperliquid leader-vault products.
Reuse the repository's Hyperliquid account-data facilities where useful, but
do not assume `vaultDetails` or native-vault transfer commands apply.

## Deposits and withdrawals

The [integration interface](https://docs.buoy.finance/developers/smart-contract-integration.md)
documents these Router calls:

```solidity
requestDeposit(address vault, address recipient, uint256 amount, uint256 minShares)
requestWithdrawal(address vault, uint256 shares, uint256 minOut)
cancelDeposit(uint256 globalId)
cancelWithdrawal(uint256 globalId)
getGlobalRequest(uint256 globalId) // vault, localId, kind
```

Deposits require USDC approval to the Router, followed by a payable request.
USDC is escrowed in the vault. The fulfiller calculates NAV, crystallises any
performance fee, mints shares and bridges capital to HyperCore. Pending
deposits can be cancelled after the configured timeout.

Withdrawals escrow shares without an ERC-20 approval, then follow
`Pending -> Locked -> Released`. Locking burns shares and records a USDC
obligation; release pays the user automatically. There is no ordinary user
claim transaction. The fulfiller bridges liquidity and may unwind positions.
A locked amount can be reduced for realised losses, bounded by `minOut`.
An adapter must therefore read the actual paid amount, not book the initial
locked amount as cash.

The [request lifecycle page](https://docs.buoy.finance/protocol-deep-dive/request-lifecycle.md)
and integration page disagree on locked cancellation: one says original
shares are restored; the other describes re-minting at the locked USDC value.
Verify the deployed implementation before modelling this recovery path.
Cancellation restores a position; it does not guarantee conversion to cash
if the fulfiller stops. Pausing can also impede requests and cancellation.

Router global IDs map to vault-local request IDs. Settlement events are
indexed by global ID rather than vault, so historical indexing needs that
mapping. Batches may emit skipped items that remain pending.

## Pricing is the main integration issue

The [NAV documentation](https://docs.buoy.finance/protocol-deep-dive/nav-and-share-price.md)
describes gross assets excluding uncredited pending deposits, then subtracting
locked withdrawal obligations to obtain the value backing shares.
Live valuation must handle the account's abstraction mode: unified accounts
already include perpetual margin and PnL in spot balances, so adding perp
account values again double-counts capital.

`totalAssets()`, `pricePerShare()` and `convertToAssets()` use cached NAV.
The integration guide explicitly warns that it can be hours or days old.
Settlement updates the cache; explicit fee crystallisation can also publish
NAV, but there is no periodic heartbeat. Always retain `latestNavTimestamp()`.
Historical RPC reads reproduce this stale cache, not a continuous market NAV.

The API provides live quotes, allocation and history. Its `tvl` is gross NAV
before locked obligations; it must not be used directly as remaining-holder
equity. Docs describe detail TVL caching for up to five minutes and list TVL
falling back to stored snapshots. Quote pricing also needs reconciliation
against fee crystallisation and share dilution before being treated as a
canonical net return series.

Observed history caveat: `metric=pps` returned fractional values near zero at
inception and approximately `0.36693` at the end of the sample, while the live
quote was approximately 1.36903 USDC/share. This suggests a normalised return
series rather than an absolute 18-decimal price. Confirm its baseline, fees,
sampling and cash-flow adjustments before importing it. Do not copy headline
APR into our metrics: Buoy documents asymmetric annualisation of gains/losses.

## API checks performed

The [REST API documentation](https://docs.buoy.finance/developers/rest-api.md)
publishes the base URL
`https://europe-west1-buoy-loan.cloudfunctions.net/app/api/v1`.
The current web bundle uses the same prefix without `/v1`; both list routes
returned HTTP 200 during this research. Prefer the documented versioned API.

Unauthenticated GET checks on 2026-11-14 succeeded for:

- `/vaults?limit=100`: 58 records, `hasMore=false`; summed reported TVL about
  USDC 39,628.46. This includes dust and apparently experimental deployments,
  so it is not a count of investable strategies.
- `/v1/vaults?limit=1`: documented versioned route reachable.
- `/vaults/{example}`: six-decimal shares/asset, 1,000 bps performance fee,
  and the documented Router/factory/USDC addresses.
- `/vaults/{example}/quote/deposit?amountUsdc=1000000`: 730,442 expected share
  units, 726,789 minimum units, price `1369033362068965517`, native fee
  `10000000000000000` wei. This is a read-only quote, not a deposit test.
- `/vaults/{example}/performance?range=all&metric=pps&resolution=1h`:
  returned historical points and `returnPct`; semantics need confirmation.

## Fees, admission and trust

The [fee schedule](https://docs.buoy.finance/for-depositors/fees.md) describes
no management fee, a per-vault high-water-mark performance fee capped at 50%,
and a fixed native request fee, currently 0.01 HYPE per deposit/withdrawal.
The protocol/referral share is a slice of the performance fee, not an extra
fee. Trading and builder costs also affect returns. Read configuration rather
than hardcoding these values.

For v3, read `policy()` and `configOf(vault)` to distinguish a depositor
whitelist from TVL caps and minimum leader ownership. Admission is per vault;
an API listing is not proof of permissionless deposits. `maxDepositFor` is
advisory and uses cached NAV; settlement rechecks against live NAV.

The [trust documentation](https://docs.buoy.finance/protocol-deep-dive/security-and-trust.md)
acknowledges that the fulfiller supplies NAV without an independent correctness
check. A nonce guards against intervening contract-state changes, not dishonest
prices or every market movement. Admins can change fees/leaders, pause vaults
and upgrade the Router. Destination restrictions do not remove valuation,
trading-loss, liquidity or Router-approval risks.

The docs link a [Shieldify report](https://github.com/shieldify-security/audits-portfolio/blob/main/reports/Buoy-Security-Review.pdf)
and [remediation notes](https://docs.buoy.finance/protocol-deep-dive/security-review-remediation.md).
The auditor's repository contains the PDF; its contents and coverage of v3
were not verified here. A search-indexed homepage mentions Zellic, while the
current docs identify Shieldify; do not equate those claims or assume current
deployment coverage.

## Proposed repository integration

1. **Discovery and metadata.** Enumerate the current factory and retained
   legacy factories using `vaultsCount`, `vaultAt`/`allVaults`, and `isVault`.
   Supplement with the API's descriptions and links. Support both documented
   `VaultCreated` event signatures through Hypersync; standard ERC-4626 event
   discovery alone is insufficient. Confirm clone implementations and versions.
2. **Read adapter.** Add a Buoy-specific `VaultBase` adapter, or reuse the
   ERC-4626 read layer only where its assumptions hold. Wire it through the
   existing classifier/factory, preserving unsupported execution status.
   Keep cached onchain and live API valuation sources explicit. Do not send
   stale cached prices into normal yield rankings as fresh observations.
3. **Prices and history.** Validate API price-history semantics first; build
   our return metrics from a validated share series. Independent reconciliation
   would combine HyperCore balances/prices with EVM balances, pending deposits,
   withdrawal liabilities and fee dilution. Historical reconstruction needs
   synchronised histories, not just today's account state.
4. **Execution.** Implement a protocol-specific `VaultDepositManager` using
   existing request/ticket/recovery interfaces. Keep Router approvals, exact
   HYPE values, ID mapping, automatic payouts, cancellation and pending-claim
   valuation in the manager. Evaluate shared queued-manager hooks against the
   actual ABI; do not assume ERC-7540 conformance or build another queue system.
5. **Guard and certification.** Extend shared guard setup for reviewed Router
   calls and cancellation, vault/recipient checks, approval target and payable
   fees. Verify current guard capabilities first. Certify only after complete
   deposit/withdrawal/cancellation lifecycles through guarded custody. Use
   shared fixed-block forks for EVM logic; a funded live check is also needed
   for real HyperCore bridging and protocol-fulfiller settlement.
6. **Publication.** Add protocol metadata, fees, risk classification, logos,
   per-vault strategy research, documentation and focused tests. If integration
   repairs persisted discovery/metadata or imports historical prices, use a new
   numbered migration with fixed scope and preserve existing state/history.

## Evidence gaps before implementation

The explorer returned HTTP 403; no Chrome tool was available. Sourcify v2
reported no match for the documented v3 implementation. Thus no verified
Solidity source was obtained and no source-level assessment is claimed.
The web bundle contains interfaces, which help identify calls but do not prove
deployed behaviour. Obtain verified sources/exported ABIs for every supported
vault version and the current Router, resolve Router implementation/admin
configuration, and reconcile documentation inconsistencies before execution.

No Python or Solidity changes were made, so no test suite, formatting run,
metadata migration or historical backfill was needed for this research note.
