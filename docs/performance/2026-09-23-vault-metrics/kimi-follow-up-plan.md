# Plan for Kimi review follow-ups

This plan follows [Kimi's max-thinking review](kimi-review.md) of the vault-cleaning and publication work in PR #1595. The [local measurements](implementation-results.md) are a starting point, not production savings. Keep each change small, measure it on the same production-format snapshot, and stop a candidate when its cost or output risk outweighs its measured gain.

The local implementation and decisions are recorded in [kimi-follow-up-results.md](kimi-follow-up-results.md). Production warm-cycle validation remains pending deployment.

## Correct the expected impact

| Finding | Current evidence | Decision |
|---|---|---|
| Repeated chain-address construction in `cross_check_data()` | The whole cross-check took 5.5–5.7s over 10.1 million hourly rows. That is an upper bound for the saving. | Pilot first. |
| JSON validation and serialisation work | Kimi estimated 2–3s; no paired measurement establishes the saving. `orjson` is already a project dependency. | Pilot `orjson` on the publication path; retain strict validation. |
| Nondeterministic flag and curator-post order | Paired exports with a fixed clock differed only in 174 flag lists and 27 equal-time post lists, plus state ordering. | Make the two list orders stable, then confirm output semantics. |
| HEAD check before Brotli compression | One quality-11 compression costs about 51s locally, but the published JSON includes a fresh `generated_at` timestamp on every run. Its source digest therefore changes even if vault data does not. | Defer digest-only skipping under the current output contract. |

The list-order differences do **not** by themselves establish avoidable production uploads: the changing `generated_at` field already makes each raw JSON payload different. Do not describe the full 51s as a likely per-round saving from a HEAD preflight.

## Work in order

1. **Make output ordering deterministic.** Do this first to make later byte comparisons useful; no time saving is assumed. Sort exported vault flags by their string value at the point where the flag set becomes a JSON list. In `VaultPostDatabase.fetch_recent_posts_by_feeder()`, order by publication time descending, then `source_id` ascending and `external_post_id` ascending in both the per-feeder `ROW_NUMBER()` window and final result order. The database primary key `(source_id, external_post_id)` makes this a unique order after the post-source join. Preserve newest-first semantics; only equal-time tie order and possibly top-N membership at a tie boundary may change. Add focused tests with multiple flags and posts tied exactly at the top-N cut-off, closing the DuckDB connection through a fixture or `finally`. Compare pre-change and post-change parsed exports: after normalising flag and equal-time post order, allow only post membership changes among entries sharing the cut-off timestamp. The old tie selection is nondeterministic, so do not require one exact pre-change membership set. Then run two post-change exports with a fixed clock and identical input: require identical public JSON bytes and parsed state objects. Record raw state-byte differences separately; they may reflect object-key insertion order rather than changed state values. Do not add a general state key sort unless a concrete consumer or upload need justifies it. Claim no upload-time saving without production evidence.

2. **Pilot the identity cross-check.** Benchmark the existing full-row string construction against building chain-address keys only for distinct `(chain, address)` pairs. Include the cost of finding distinct pairs over all 10.1 million rows. Keep the existing behaviour: report each distinct missing chain-address key once, with the same message text and case-sensitive `astype(str)` conversion, including null values. The current check does not validate `id`; a mismatched `id` with a valid chain/address must keep its current result. Do not substitute `id` alone. Add focused cases for duplicates, missing metadata, mismatched `id`, and null chain/address. Run three alternating reference/candidate process pairs on the same snapshot, report median and range of whole cross-check time and process peak RSS using `/usr/bin/time -v`. Accept only a median saving of at least 1s with no more than 0.5 GiB extra peak RSS and no behaviour change; otherwise leave the code alone.

3. **Pilot `orjson` for publication JSON.** Time strict validation and JSON writing separately on the full export. Keep the existing recursive validator, which rejects non-string keys, non-finite floats and unsupported types with nested error paths. Compare the current standard-library `json.dump()` path with `orjson.dumps(..., option=orjson.OPT_INDENT_2)` and an atomic binary write. `orjson` is already declared in `pyproject.toml`; it returns bytes and converts NaN to `null` by default, so removing the validator would change the export contract. Before switching, test every type the validator permits against both encoders, including integers beyond 64 bits, NumPy scalar subclasses, Unicode edge cases, dates and decimals; the full snapshot alone cannot prove future compatibility. Use `orjson` only where the current values and failure behaviour are preserved; retain the standard-library path for values `orjson` cannot encode without changing their meaning. Require parsed-value parity and inspect any byte differences, including float formatting and escaping; prefer byte-identical output where the current format permits it. Preserve atomic replacement and the rule that freshness state is written only after the public JSON. Test nested invalid types, NaN, infinity and non-string keys; each failure must name the field and leave the prior file and freshness state intact. Run three alternating reference/candidate process pairs; report median and range of whole validation-plus-write time and process peak RSS using `/usr/bin/time -v`, which includes native allocations. Accept only a median saving of at least 2s, no more than 0.5 GiB extra peak RSS, and no unintended output or error-behaviour change. Otherwise reject the pilot. If accepted, check nearby sticky-state and metrics-state JSON writes for safe `orjson` replacements. Keep their standard-library reads unless copies of existing production state and corrupt-file behaviour establish parity, including the metrics state's quarantine path. Leave unrelated JSON paths alone.

4. **Leave compression preflight deferred.** The new `generated_at` value makes source bytes change on each run, so the proposed digest-only HEAD check cannot skip ordinary publications. If at least three complete publication artefacts are already retained, compare them offline after excluding `generated_at` to estimate how often substantive content repeats. If none repeat, close this idea without code. If content repeats often, write a separate proposal for consumer freshness expectations, source-digest meaning, compressed-length and MD5 checks, and failure fallback. Do not weaken the shared R2 upload helper or add production instrumentation for this pilot. A Brotli quality-versus-size experiment is a separate possible proposal, not part of this plan.

## Validation and scope

Use focused tests and paired local runs for each accepted code change. For output ordering, compare exact public JSON bytes as well as parsed values; for cross-check and `orjson` pilots, record whole-stage time and peak RSS, not just a microbenchmark. After deployment, compare the median phase timings of at least three warm cycles before and three after, along with due-vault counts and both publication buckets. Keep the accepted changes in a small follow-up PR; leave rejected pilots documented without carrying experimental code into production.

Kimi's suggestions to omit `block_number` and parallelise the metric loop are out of scope. Metrics read the first and last block numbers, and the previous process-pool trial hit deadlocks or memory exhaustion on production-shaped data. The earlier review's Yearn benchmark gap, logging concern and positional-alignment documentation have already been addressed in #1595.

Claude Opus 5.5 reviewed the draft and revisions on 23 September 2026. Its actionable points led to the explicit byte-parity scope, numeric pilot gates, equal-time cut-off membership rule, unchanged `id` semantics, retained strict JSON validator, and offline-only compression decision above. The `orjson` revision was also reviewed; its compatibility findings led to the encoder type matrix and production-state read gate. The review incorrectly assumed default JSON write settings for the current state files: both state writers use `allow_nan=False`, and the public export uses `ensure_ascii=False`. Its final pass found no blocking issues.
