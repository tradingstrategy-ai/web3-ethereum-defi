# Kimi follow-up implementation results

These measurements use the same 10,116,623-row production-format local snapshot as [the earlier work](implementation-results.md). They are isolated runs on vitalik8 with a fixed 23 September 2026 clock, not production scanner-cycle or R2 network timings. The [plan](kimi-follow-up-plan.md) set the acceptance gates before the pilots.

| Change | Local result | Decision |
|---|---|---|
| Check distinct chain/address pairs instead of building strings for every hourly row | Median **5.610s → 0.357s** across three interleaved runs per variant; 5.253s saved (93.6%). Peak RSS was similar. | Kept. The integrated warm run measured about 1.0s for the cross-check. [Measurements](kimi-cross-check-results.json) |
| Use `orjson` for public JSON and sticky-state writes, retaining strict validation | Combined median validation and write time **3.633s → 1.108s** across three interleaved runs per file and variant; 2.525s saved. Peak RSS changed by only a few MiB in the isolated process. | Kept for these two files. Parsed values matched; raw bytes differed, including equivalent number spelling. [Measurements](kimi-json-write-results.json) |
| Stable vault flags, equal-time curator posts and the three top-level publication maps | Two independent warm exports produced equal parsed public JSON and sticky state. Their public byte differences were confined to key order in `core3_protocols`, `xerberus_protocols` and `curators`; sorting those maps made the bytes identical. | Kept. A final integrated export produced the same SHA-256, `e6ad935c388ceee8ebe43ac9cc0d467571a6d84b3ab6fec7dd5b51c4708e0e73`. |
| Brotli digest-only HEAD preflight | Every public JSON contains a newly generated `generated_at` field, so its source digest changes each run. The retained local exports use a fixed clock and cannot establish real unchanged-cycle frequency. | Deferred as planned. No R2 helper or publication contract was changed. |

The three complete warm runs took [179.0s](kimi-warm-a.json), [175.3s](kimi-warm-b.json) and [173.6s](kimi-warm-c.json), with 5,765 vaults due, 5,431 exported rows and 8.24–8.28 GiB peak RSS. Their [logs](kimi-warm-c.log) record phase progress. The earlier 184.4s run used a different copied freshness-state generation, so the whole-export difference is indicative rather than a paired estimate of these changes.

Against the earlier exporter, the final parsed public JSON differed only in 184 flag-list orders, 29 recent-post orders and seven curator post selections where old and new posts shared the exact top-N cut-off timestamp. All other compared values matched. The old tie selection was nondeterministic. The first two new full exports had identical sticky-state bytes; their metrics-state objects parsed equally despite key-order differences. The final export's public JSON bytes matched the canonicalised first two exports exactly.

The writer keeps the path-aware strict validator because `orjson` would otherwise turn NaN into `null`. If `orjson` rejects a value accepted by the prior writer, such as an integer wider than 64 bits or a NumPy float scalar, it falls back to the standard-library writer. Metrics-state writing and both state readers still use the standard library: the small metrics file did not justify a separate change, and changing state readers would require production-file and corruption-path parity checks.

Focused feed, sticky-export, identity, flag and freshness tests passed (50 tests). After a read-only Claude Opus 5.5 code review found no high-confidence bug, the tests were tightened for pandas-version-specific null rendering and for a failed public write leaving both persisted state files intact. The standard JSON fallback now logs a warning if a future value disables the fast path. Formatting and focused import/lint checks passed; `vault_metrics.py` still has three pre-existing unused-variable lint findings outside the changed lines. No production scan or R2 upload was run.
