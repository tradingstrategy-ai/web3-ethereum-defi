# Repository-supplied Anvil fork RPC cache seed

Committed Foundry (Anvil) fork RPC cache files, so **every** runner — GitHub
Actions, other CI, and local first runs — starts warm for the canonical
`*_MIDNIGHT_BLOCK` fork blocks instead of cold-fetching from (and being throttled
by) the upstream archive node. This is the **primary** warm-cache mechanism; the
workflows carry no `actions/cache` step for the fork RPC cache.

The `_seed_foundry_rpc_cache` session fixture (`tests/conftest.py`) copies this
tree into `~/.foundry/cache/rpc` before any fork launches. See
`eth_defi/testing/rpc_cache.py` (the mechanism), `eth_defi/testing/README.md`
section 5 (how to regenerate/update/purge), and
`docs/README-test-suite-performance.md` (why it matters).

Anvil only writes these files on a graceful shutdown, so regenerating the seed
depends on the graceful-shutdown behaviour in `AnvilLaunch.close()`.
The committed seed is captured with the CI-pinned Foundry/Anvil release
(`v1.8.6` since 2026-10-27, previously `v1.3.2`). Anvil `v1.8` reads and writes
per-endpoint `storage-<keccak256(fork_url)>.json` files; the launch code aliases
the committed `storage.json` to that name, with `meta.source_id` rewritten for
the launch's fork URL, and merges it back on shutdown, so
seeds keep the release-agnostic `storage.json` name here. Do not mix a seed generated by another
release into the test cache without running the affected integration tests.

## Layout

Mirror Foundry's on-disk cache layout exactly — keyed by Foundry's **network
name** (not chain id), then block, then the cache file:

```
rpc_cache_seed/
  mainnet/24496689/storage.json  # Ember redemption lifecycle
  mainnet/25598869/storage.json
  mainnet/26234307/storage.json  # Flying Tulip ssftUSD post-deployment characterisation
  mainnet/26279104/storage.json  # Lagoon v0.5.2 production characterisation
  arbitrum/487039644/storage.json
  base/30659990/storage.json  # Lagoon Base lifecycle characterisation
  base/49030926/storage.json
  base/51649628/storage.json  # Lagoon v1 production characterisation
  bsc/111758906/storage.json  # BUSD fork state for tests/rpc/test_anvil.py
  ...
```

At session start `seed_default_foundry_rpc_cache()` copies this tree into
`~/.foundry/cache/rpc/`, **never overwriting** an existing (warmer) live file.

was observed failing, and is required by
`tests/lagoon/test_lagoon_v1.py`. The canonical Base midnight block predates
that deployment, so replacing this seed with a midnight block would not test
the production compatibility boundary.

`mainnet/26279104/` is the fixed Ethereum block at which the production

## Capturing a seed file

`arbitrum/518876926/` covers Nova Markets' Conviction Pool metadata and the
GuardV0 deposit, withdrawal-request, epoch-settlement and claim lifecycle in
`tests/erc_4626/vault_protocol/test_nova_markets.py`. The canonical July block
predates the pool, so this fixed October block is an intentional exception.
The seed contains actual vault, USDC and PnL-feed state reads, plus the proxy
implementation slot and implementation runtime used to pin the fee review.
It was refreshed with CI-pinned Anvil v1.8.6 on 2026-10-28 after the complete
Nova fork group passed on the merged branch.

1. Run the relevant fork test locally against a responsive archive provider so
   Anvil populates `~/.foundry/cache/rpc/<network>/<block>/`.
2. Copy the resulting `<network>/<block>/` directory here, keeping the layout.
3. Keep files small and dense — canonical midnight blocks plus explicitly
   justified fixed-block characterisation exceptions such as the Lagoon v1
   block above. Do not commit mutable-tip (`latest`) fork caches; they are
   non-reproducible and never re-used.

An external (uncommitted, larger) seed directory can also be supplied at runtime
via the `ETH_DEFI_RPC_CACHE_SEED_DIR` environment variable.

## Archive bootstrap and cache invariant

Stored state covers repeatable historical reads after Anvil starts, but this is
not a fully offline replay. The initial chain-identity check, any enabled
archive-availability check, and every cache miss are necessarily remote. With
multiple providers, they must use the same bounded failover proxy as Anvil; no
setup check may make the first provider a single point of failure. To refresh a
seed, start with an empty Foundry cache directory, run its complete fixed-block
integration group, then commit the `storage.json` written when Anvil closes
cleanly.

## Failure modes

Use the [Anvil failure modes](../README.md#anvil-failure-modes) section for the
full classification and recovery procedure. The short version is:

- HTTP 500, `header for hash not found`, or a timeout that disappears on a
  warm local rerun indicates an upstream provider/cache miss. Add failover and
  store the missing replies in the seed.
- A local Anvil process that remains unresponsive after upstream requests have
  completed is a process wedge. Close and relaunch it; increasing the archive
  timeout does not repair a dead local process.
- A timeout in `anvil_loadState` while restoring a checked-in state file is a
  Foundry/Anvil saved-state compatibility issue. Keep the state file, seed, and
  binary on the same pinned release.

The observed Foundry-version failures, the successful `v1.3.2` combination,
and representative tracebacks are documented in
[`PR #1589`](https://github.com/tradingstrategy-ai/web3-ethereum-defi/pull/1589).
